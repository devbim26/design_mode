# Дизайн: Image Studio на devbim.com — Google-вход, роли, личные воркспейсы

Дата: 2026-10-01. Статус: согласован с пользователем (brainstorming-сессия).

## Контекст и задача

DevBIM Image Studio (патченный InvokeAI 6.2.0, вся генерация в облаке через
ImageRouter) публикуется через Cloudflare-туннель как `design.dev-b-im.com`
и защищена одним общим паролем (`SiteAuthMiddleware`, `SITE_PASSWORD`).
Модель пользователей в InvokeAI 6.2 отсутствует: борды, картинки, аплоады,
очереди — общие, поля «владелец» нет. Сайт devbim.com — отдельное SPA
(React/TSX) со своим бэкендом, вход через Google, компании/тарифы/роли.

Требования пользователя:

1. Студия живёт **на devbim.com как отдельная страница** кабинета.
2. Авторизация — Google-входом devbim.com (без второго логина).
3. Права разграничены: обычный пользователь / админ.
4. У каждого пользователя — **свой воркспейс с ассетами**
   (галерея/борды, загрузки, IFC, 3D, PDF); админ видит всё.

Разделение работ: **студию делаем в этом репозитории**; разработчику
основного сервиса devbim.com передаём репозиторий + ТЗ на интеграцию
(эндпоинт токена, iframe-страница, DNS) — `docs/INTEGRATION-devbim-com.md`.

Выбранные решения (из brainstorming):

- Встраивание: **iframe-страница `/designing/image-studio`** в кабинете
  devbim.com; студия переезжает на поддомен **`studio.devbim.com`**
  (требование same-site для куки в iframe; `dev-bim.com` — чужой домен).
- Изоляция: **оверлей-мидлварь** (вариант 1 из трёх рассмотренных;
  «инстанс на пользователя» отвергнут из-за 0,5–1 ГБ ОЗУ на юзера,
  «форк схемы БД InvokeAI» — из-за хрупкости при переустановке пакета).
- Роли: **2 роли** `admin` / `user`, приходят из токена devbim.com.
- Воркспейсы: **только личные** (без общих пространств компании — задел
  на будущее, как и в спеке мультитенантности).

## Архитектура

```
devbim.com (SPA, Google-вход)                 studio.devbim.com (эта студия)
┌────────────────────────────┐                ┌──────────────────────────────┐
│ /designing/image-studio    │                │ ASGI-мидлварь StudioAuth:    │
│  1. fetch studio-token     │───JWT t=?───▶  │  /auth/sso: HS256+jti        │
│     (свой бэкенд)          │   iframe       │  → user в overlay-БД         │
│  2. iframe ────────────────│─────────────▶  │  → кука devbim_session (12 ч)│
└────────────────────────────┘                │ фильтрация API по владельцу  │
                                              │ + тегирование созданий       │
                                              │ + патч sockets.py (room/user)│
                                              │ overlay: data/studio.sqlite  │
                                              └──────────────────────────────┘
```

Один процесс студии. Режимы работы мидлвари (`STUDIO_AUTH_MODE`):

- `password` (по умолчанию) — прежнее поведение: один пароль на инстанс.
  **Локальные компании-лицензиаты (порты 9100+) не затрагиваются.**
- `sso` — режим для devbim.com: весь механизм из этой спеки.

## Аутентификация (SSO-хендшейк)

Токен — JWT HS256 (PyJWT 2.15 уже в venv), секрет `STUDIO_JWT_SECRET`
(≥32 символов, одинаковый со стороной devbim.com, передача вне канала).

Claims: `sub` (ID пользователя сайта, строка), `email`, `name` (опц.),
`picture` (опц.), `role` (`admin|user`), `iat`, `exp` (≤10 мин,
рекомендуется 5), `jti` (UUID — одноразовость, кеш в памяти с TTL = exp).

Поток:

1. `GET /auth/sso?t=<JWT>` — проверка подписи, `exp`, `jti` (replay → 401).
2. Валиден → в оверлей-БД создаётся/обновляется пользователь
   (`user_id=sub`, email, имя, роль; `last_seen`), выдаётся кука,
   редирект на `/`. Токен из адресной строки исчезает (редирект).
3. Кука `devbim_session`: HMAC-подписанная (`STUDIO_SESSION_SECRET`,
   при отсутствии — `STUDIO_JWT_SECRET`), значение `user_id|issued|sig`;
   HttpOnly, Secure,
   SameSite=Lax, Path=/, TTL `STUDIO_SESSION_TTL` (по умолчанию 12 ч).
   **Роль в куке не хранится** — читается из БД на каждом запросе:
   смена роли на сайте подхватывается без перелогина; отзыв пользователя
   (флаг в БД из админ-панели) — на следующем же запросе.
4. Ошибки (истёк/кривая подпись/replay) → HTML-страница
   «Откройте Image Studio из кабинета devBIM» + мелкая ссылка
   «Вход администратора» → форма пароля `SITE_PASSWORD` → сессия admin.
   Это же — прямой вход владельца без devbim.com.
5. `GET /auth/logout` — сброс куки.
6. Вебсокеты: без валидной сессии — close 4001 (как в текущей мидлвани).
7. Мидлварь добавляет `Content-Security-Policy: frame-ancestors`
   из `STUDIO_FRAME_ANCESTORS` (по умолчанию `https://devbim.com`
   + `http://localhost:*` для отладки) — встраивание чужими сайтами
   невозможно. В password-режиме CSP не добавляется.

Старая кука `devbim_auth` не признаётся — все перелогиниваются заново
(переход единичный, пользователей мало).

## Роли и права

Источник роли — claims токена; локальное переопределение — в админ-панели
(`role_override` в БД побеждает токен). Mapping «кто admin» решает бэкенд
devbim.com (email'ы devBIM → admin, остальные → user).

| Возможность | user | admin |
|---|---|---|
| Генерация, канвас, аплоады, референсы | ✅ | ✅ |
| Галерея/борды | ✅ только свои | ✅ все воркспейсы |
| IFC / PDF / 3D Design | ✅ свои файлы/джобы | ✅ все |
| Style presets | чтение | чтение + запись |
| Workflows | чтение | чтение + запись |
| Model Manager (ключи, модели) | ❌ | ✅ |
| Меню «Настройки» | ❌ скрыто | ✅ |
| Админ-панель `/admin` | ❌ | ✅ |

Существующий гейт Model Manager паролем `ADMIN_PASSWORD` превращается
в проверку роли (пароль остаётся запасным входом для прямого доступа —
см. §Аутентификация п.4). Сокрытие «Настроек» для не-админов — развитие
текущих JS-патчей `patch_admin_gate` (App-бандл).

## Оверлей-БД владения

`data/studio.sqlite` (режим WAL, короткие транзакции), только в SSO-режиме;
создаётся автоматически при первом старте.

- `users(user_id PK, email, name, role, role_override NULL, revoked INT,
  created_at, last_seen)`
- `ownership(kind TEXT, key TEXT, user_id TEXT, PRIMARY KEY(kind, key))`
  - `kind`: `image` (имя картинки), `board` (board_id), `batch` (batch_id),
    `ifc` / `pdf` / `threed` (имя файла / job_id).

Тегирование (кто пишет владение):

1. Мидлварь: `POST /api/v1/images/upload` (аплоады канваса, маски,
   референсы), `POST /api/v1/boards/` (создание борда).
2. ImageRouter-прокси (`imagerouter_router.py`): при перехвате
   `enqueue_batch` записывает `batch → user` (контекст запроса доступен);
   после `services.images.create` (два места: canvas- и upscale-генерация)
   записывает `image → user`.
3. Кастомные роутеры IFC/PDF/3D: пользователь приходит из мидлвани
   (внутренний заголовок/`request.state`), тегируют свои файлы и джобы.

Локальных моделей нет (вся генерация облачная), поэтому перехват
`enqueue_batch` покрывает 100 % генераций — «дыр» без владельца не остаётся.

Легаси-контент (существующая галерея/борды инстанса): кнопка в админ-панели
«назначить легаси-контент мне» проставляет владельцем admin для всех
записей без владельца (разовая миграция, идемпотентна).

## Изоляция HTTP API

Мидлварь фильтрует ответы только для не-админов (admin видит всё
без фильтров). Перечень точек (уточняется при реализации, но закрыть
обязаны все):

- `GET /api/v1/boards/` — фильтр списка по владению;
- `GET /api/v1/boards/{id}` — чужой → 404;
- `POST /api/v1/boards/` — тег; `DELETE`/`PATCH` борда — проверка владельца;
- `GET /api/v1/images/` (листинг; `board_id=none` = «Все изображения») —
  фильтр `items` по владению, пересчёт `total` (механика пере-упаковки
  JSON ответа — как `_proxy_json` в ImageRouter-роутере);
- `GET /api/v1/images/i/{name}/full|thumbnail|metadata|…`,
  скачивание, `DELETE`/`PATCH` картинки — чужое → 404;
- bulk-download — проверка каждого запрошенного файла;
- `GET /api/v1/session_queue/*` (списки очереди/сессий) — фильтр по
  своим `batch` (вкладка очереди в UI скрыта, закрываем API-дыру);
- запись style presets / workflows / модели — по роли (см. таблицу).

## Изоляция сокет-событий

Патч `sockets.py` (setup-скриптом, бэкап `*.studio-bak`, идемпотентно):

- обработчик `connect`: разбор куки сессии из `environ` →
  `enter_room(sid, "user:<id>")`; без сессии соединение уже закрыто
  мидлварью (ASGI-уровень);
- обёртка над эмитом queue-событий (`_handle_queue_event`): владелец
  определяется по `image_name` (в `InvocationCompleteEvent`) или
  `batch_id` из оверлей-БД → событие эмитится **только в room
  `user:<владелец>`** вместо общего room `queue_id` (все браузеры сидят
  в queue `default` — без этого каждый видел бы чужие картинки и прогресс);
  владелец не найден → прежнее поведение (системные события);
- model-события остаются глобальными (локальных моделей и установок нет).

## Кастомные роутеры (IFC / PDF / 3D)

Роутеры наши (`ifc/`, `pdf/`, `threed/` — развёрнуты в site-packages):
мидлварь прокидывает пользователя, списки (`/api/v1/ifc/list` и т.п.)
фильтруются по владению, загрузки/джобы тегируются. Style presets —
общие на чтение, запись только admin.

## Админ-панель и баннер

- `/admin` — HTML-страница из мидлвари (как login-страница), только для
  admin: таблица пользователей (email, имя, роль, счётчики картинок/бордов,
  `last_seen`), действия: переопределить роль, отозвать пользователя
  (флаг `revoked`), «назначить легаси-контент мне».
- Баннер (`devbim_banner.js`, верхний «devBIM — Design»): справа email/имя
  + роль + «Выйти»; данные — новый лёгкий эндпоинт `GET /api/v1/studio/me`
  (текущий пользователь, только в SSO-режиме).

## Развертывание

- `setup_site_auth.py` (существующий порядок setup-скриптов сохраняется):
  разворачивает новую мидлварь + патчит `sockets.py`; добавляет ключи
  в `.env`, если их нет. Идемпотентно.
- Новые ключи `.env`: `STUDIO_AUTH_MODE` (`password|sso`, по умолчанию
  `password`), `STUDIO_JWT_SECRET`, `STUDIO_SESSION_SECRET` (опц.;
  при отсутствии используется `STUDIO_JWT_SECRET`), `STUDIO_SESSION_TTL`
  (сек, 43200),
  `STUDIO_FRAME_ANCESTORS`.
- Туннель: `~/.cloudflared/config-design.yml` — hostname
  `studio.devbim.com` (вместо/рядом с `design.dev-b-im.com`); DNS
  на стороне devbim.com (CNAME на туннель) — в ТЗ.
- Хостинг у разработчика сайта: `launch/start_server.sh` (Linux-запуск
  того же стека) + раздел README «Деплой studio.devbim.com»
  (Python 3.11+, ~1 ГБ ОЗУ, генерация облачная).
- До интеграции с сайтом: локальное тестирование утилитой
  `tools/mint_test_token.py` (минт тестового JWT с заданными claims);
  текущий домен продолжает работать в password-режиме.

## ТЗ для разработчика devbim.com (deliverable)

Файл `docs/INTEGRATION-devbim-com.md` в корне репозитория:

1. Эндпоинт токена на бэкенде сайта (за Google-сессией): выдаёт JWT
   HS256, claims ровно как в §Аутентификация; секрет передаётся вне канала.
2. Страница `/designing/image-studio`: fetch токена при открытии →
   `iframe src="https://studio.devbim.com/auth/sso?t=…"`,
   `allow="clipboard-write; fullscreen"`, `referrerpolicy="no-referrer"`,
   высота на весь экран контента.
3. DNS: `studio.devbim.com` → туннель/сервер студии.
4. SHOULD: слушать postMessage `studio:expired` от iframe и перезагружать
   его со свежим токеном (студия шлёт событие, когда сессия истекла).

## Ошибки и edge-cases

- Истёкший токен / кривая подпись / replay `jti` → страница «войдите
  заново из кабинета» (+ postMessage `studio:expired` в родитель).
- Вебсокет без сессии — close 4001 (текущее поведение сохраняется).
- Конкурентный доступ к sqlite — WAL + короткие транзакции; БД открывается
  лениво, при сбое чтения владения — fail-closed (404) для user-запросов.
- Перезапуск сервера не убивает сессии (кука подписанная, не in-memory);
  кеш `jti` переживает рестарт не обязан (токены живут минуты).
- Пользователь удалён на сайте — живёт до конца TTL либо до отзыва
  в админ-панели (проверка `revoked` на каждом запросе).
- Первый вход создаёт пустой воркспейс (без автосоздания бордов —
  встроенной галереи «All Images» и ручного создания бордов достаточно).

## Проверка

Тесты (`venv\Scripts\python.exe tests\<имя>`, plain asserts):

- `tests/test_studio_auth.py`: валидный токен → кука; истёкший `exp` →
  401; неверная подпись → 401; повторный `jti` → 401; пароль-вход →
  admin; `revoked` пользователь → отказ; password-режим не тронут.
- `tests/test_studio_ownership.py`: тег upload/борда/картинки;
  фильтрация листингов (свои видно, чужие нет, `total` корректен);
  чужой URL картинки → 404; admin видит всё; легаси-миграция.
- `tests/test_studio_sockets.py`: два «пользователя» в разных комнатах —
  событие complete уходит только владельцу.

Ручной чек-лист: два браузера = два пользователя (генерации/галереи
не пересекаются, прогресс не прыгает); вход админом по паролю;
переопределение роли в `/admin`; проверка парса JS-бандлов после патчей
(`node -e "import('file:///...index-*.js')..."` — только runtime-ошибка);
перезапуск сервера `launch\_restart_server.ps1`.
