# Спека: системное улучшение извлечения геометрии image→IFC (threed, п.60)

Дата: 2026-09-26 · Статус: предложено (не реализовано) · Ветка: 3d_analysys

## 1. Постановка

Задача пользователя: системно улучшить извлечение геометрии из загруженной
картинки по темам **фасад / интерьер / генплан** и дальнейшее построение
соответствующего IFC. Цель — максимально точная геометрия. Допускается
архитектурное изменение конвейера; предложенный пользователем вариант —
**2 прогона на разных моделях и скриптах** с последующим сведением.

## 2. Текущее состояние (кратко; детали в HANDOFF пп.35–58)

Конвейер «3D Design»: модалка → job-API (`POST /api/v1/threed/generate`,
фоновые потоки, поллинг) → tiered VLM-конвейер п.56:
**analysis** (astra, параметрический JSON-сценарий по теме) →
**контракт посадки** (детерминированный `validate_interior`, ремонт JSON
без картинки на luna → sol) → **сборка IFC4** (ifcopenshell, 4 билдера:
plan/facade/interior/scene) → **verify** (судья-VLM на своей модели,
вердикт {ok, issues}) → **петля CORRECTIONS** (≤2 попытки) →
**эскалация** (одна финальная попытка дороже моделью) → победитель по
рангу → автозагрузка в IFC-вьювер. Плюс п.58: детерминированные
структурные проверки IFC (`structural_report`: проёмы без Voids/Fills,
элементы без пространственной привязки и т.д.).

Файлы: `threed/threed_router.py` (745), `threed/threed_scenarios.py`
(1177), `threed/threed_build.py` (1450), `threed/threed_verify.py` (257),
деплой — `setup_threed.py` (копирует файлы в
`venv/Lib/site-packages/invokeai/app/api/routers/`, патчит `api_app.py`).

### Зафиксированные ограничения (почему меняем архитектуру)

1. **Узкое место доказано (п.45)**: качество VLM-анализа — позиции/форма/
   размеры деталей, а не выразительность схемы и не конвейер.
   Judge-score 35→43, цель 55–60 не достигнута.
2. **Один извлекатель**: одна модель + один параметрический промпт;
   координаты VLM пишет «по памяти» — систематически неточные.
   Grounding-модели (Qwen2.5-VL и т.п.) выдают боксы в пикселях —
   потенциально более точные; требует измерения зондом (задача 1b).
3. **Verify слепой**: судья получает текстовые счётчики
   (scene_overview/built_overview), но НЕ видит наложение извлечённой
   геометрии на картинку → смещения сетки окон/контуров петля не ловит.
4. **Валидаторы клампят, но не регуляризуют**: нет снапа к
   ортогональности, ритму, симметрии, типовым размерам.
5. **Двухканального извлечения нет**: ярусы п.56 последовательны,
   кросс-проверки двух независимых извлечений (разные модели + разные
   промпты) нет. При этом `_call_vlm(system, prompt, image_url, model)`
   принимает модель на каждый вызов, в каталоге ImageRouter ~120 VLM —
   вторая модель штатно доступна. Ансамбль/self-consistency (Wang 2023,
   MDPI 2025) здесь НЕ применим — там N сэмплов одной модели + голос;
   наш случай — **dual extraction + arbitration cascade** (Gupta 2019,
   Ashery 2024).

## 3. Изученные внешние подходы (исследование 26.09)

- **Grounding-VLM**: Qwen2.5-VL возвращает боксы в абсолютных пикселях
  `[x1,y1,x2,y2]` — лучший кандидат на «прогон B»; grounding-способность
  конкретных моделей каталога ImageRouter обязана мерить зондом, не
  предполагать.
- **Facade parsing** (SAM-модели: BuildWin-SAM 2025; классика DeepFacade)
  и **room layout** (HorizonNet, LGT-Net, uLayout CVPR'25) — сильны, но
  требуют GPU-инференса; наш хост CPU-only → вне скоупа продукта.
- **Metric depth / 3D-фундамент-модели** (UniDepth V2, Metric3D v2, VGGT
  CVPR'25 Best Paper) — та же причина: CPU-инференс минуты.
- **MCP для IFC**: ifc-bonsai-mcp/MCP4IFC (через Blender+Bonsai) —
  отклонён базовой спекой 18.09 (лишняя тяжёлая зависимость); паттерны
  Daviidro/ifcopenshell-mcp и smartaec/ifcMCP уже взяты в п.58
  («подход, не код»). Нового MCP не нужно.
- **Двухканальное извлечение + arbitration cascade**: ближе к
  «cooperative multi-agent» (Ashery et al. 2024, LLM-Blender) и
  «model cascade» (Gupta et al. 2019), чем к классическому
  self-consistency (Wang et al. 2023). Self-consistency и Ensemble LLMs
  survey (MDPI 2025) описывают N сэмплов ОДНОЙ модели + голосование;
  у нас РАЗНЫЕ модели + РАЗНЫЕ промпты + детерминированное сравнение
  + LLM-арбитр только по спорным полям. Метрика `agree_rate` — наша,
  не из этих обзоров.
- **Генпланы из аэро/спутника**: SpaceNet/solaris — сегментационные
  сети, GPU; для нас ближе подход скилла image-to-ifc (якоря масштаба:
  парковка 2.5×5 м, спортплощадка 16–18×32–36 м) + МНК по всем якорям.

## 4. Целевая архитектура

```
картинка → прогон A: параметрический JSON (astra, текущие SYSTEM_* промпты)
         → прогон B: grounding-боксы [x1,y1,x2,y2] в пикселях (модель B из зонда)
                    → детерминированный конвертер боксы→сцена
         → compare+merge (детерминированное сравнение сцен; споры → дешёвый реферти)
         → регуляризация по теме (снапы/ритм/симметрия — чистый код)
         → контракт посадки (есть) → сборка IFC (есть)
         → визуальный verify: оверлей геометрии поверх картинки + судья
         → петля CORRECTIONS (есть) → победитель по рангу (есть)
```

Принцип: **VLM выбирает семантику, код считает геометрию**.
Порядок тем: фасад первым (узкое место доказано), затем генплан, затем
интерьер.

## 5. Задачи

### Задача 0. Спека + план (docs/superpowers/) — этот документ
Зафиксировать: диагноз, схему «2 прогона × разные модели и скрипты»,
метрики приёмки, отклонённые альтернативы (локальный CV на CPU — минуты
инференса; MCP4IFC/Bonsai — Blender, отклонён базовой спекой; меш-сервисы
Meshy/Tripo — вне скоупа).

### Задача 1a. Эталонная разметка GT-боксов (гейт зонда)
Без ground-truth IoU = 0 для всех кандидатов → двухканальное извлечение
выпадает в fallback (1b) и смысл зонда теряется. Поэтому ДО запуска
любых моделей готовим разметку.

`data/probe/_threed_ground_gt.json` — массив записей:
```json
[{"image": "vlm_test_house.png", "scenario": "facade",
  "boxes": [
    {"label": "window", "x1": 412, "y1": 188, "x2": 478, "y2": 268}
  ]},
 ...]
```

Минимум: 1 фасад с сеткой окон ≥ 8 шт, 1 план ≥ 3 корпуса, 1 интерьер
≥ 3 комнаты + 2 двери. Источник: ручная разметка автора или пользователя
(`tools/labelImg` или прямо в JSON с пересчётом боксов из скриншота).
Sanity: вспомогательная функция `_compute_iou(pred, gt)` стабильно
возвращает ≥0.9 для боксов, нарисованных «для теста» вручную.

### Задача 1b. Зонд grounding-моделей — ГЕЙТ для модели B
`data/probe/_probe_threed_ground.py` (паттерн существующих зондов
`data/probe/_vlm_probe.py`, `data/probe/_e2e_*.py`). Кандидаты из
каталога ImageRouter (`/v3/models?input_modalities=image&output_modalities=
text`, фильтр `_vlm_list_cached` уже есть):
- qwen-vl семейство (нативный grounding в абсолютных пикселях);
- `openai/gpt-6-sol` (средний ярус, проверяем grounding-способность);
- контроль — `openai/gpt-6-astra` (та же модель, что анализ A).

Промпт: строгий JSON `{"boxes": [...]}` с боксами окон/контура/зданий/
комнат. На каждую картинку GT — каждый кандидат, метрики:
- **IoU** (mean и median по `boxes[]`) — основная;
- **полнота** (recall = доля GT-боксов с IoU ≥ 0.5);
- **точность** (precision = доля предсказанных боксов с IoU ≥ 0.5);
- **валидность JSON** (доля ответов, прошедших `extract_json`).

Выход: дефолт `THREED_ENSEMBLE_MODEL` (= кандидат с лучшим mean IoU);
таблица результатов в `data/probe/_probe_threed_ground_results.json`;
констаты (короткий абзац) в спеку — какой кандидат победил и почему.
Бюджет: 3 кандидата × 3 картинки × ~2K токенов = ~$0.10–0.30.

**Fallback при провале зонда**: если лучший mean IoU < 0.5 ИЛИ доля
валидного JSON < 0.5 → прогон B переключается на текстовый
параметрический промпт на другой модели (например, `THREED_REPAIR_MODEL`,
если она доступна; иначе sol). Двухканальный режим остаётся — он ловит
галлюцинации и без grounding, только с меньшей точностью позиций.

### Задача 2. `threed/threed_ground.py` — прогон B (grounding-скрипт)
- `SYSTEM_GROUND_FACADE` / `_PLAN` / `_INTERIOR`: только боксы в пикселях
  после даунскейла ≤1536 (тот же контракт, что у текущих промптов) +
  минимум текстовых полей (floors, use, roof — вторым блоком ответа).
- Детерминированные конвертеры (чистые функции):
  - **facade**: кластеризация оконных боксов по строкам (y-центры) и
    столбцам (x-центры) → `rows/cols/w_m/h_m/margins/skip`; масштаб из
    якоря двери/этажа; `width_m` из крайних боксов; контур — бокс обводки.
    **Голосует только за `width_m`, `storeys`, `floor_height_m`,
    `rows×cols` главной сетки окон, `doors[]`**. Не участвует в решении
    по `towers/dormers/chimneys/entrance/custom_parts` — там VLM-A
    остаётся единственным источником (конфигурации grounding-сетка не
    покрывает; п.45 ввёл эти поля).
  - **plan**: боксы зданий → полигоны (ортогонализация: снап рёбер к
    0/90 с окном ±15°, остальные рёбра — `min(α, 90−α)`; RDP упрощение
    только при > 8 вершин). Масштаб по якорям из скилла
    `tools/image-to-ifc` (`tools/image-to-ifc/SKILL.md`: парковка
    2.5×5 м, спортплощадка 16–18×32–36 м); этажность/тип — из
    текстового блока ответа VLM.
  - **interior**: боксы комнат → прямоугольная сетка стен (объединение
    смежных рёбер с допуском толщины из п.55); двери — боксы на стенах,
    `x_px` вдоль стены. Кламп посадки проёмов использует константы
    `OPENING_MIN/HOST/MARGIN` из п.55 (общий импорт, дублировать
    нельзя — тесты п.55 assert'ят точные значения 6.95).

### Задача 3. `threed/threed_ensemble.py` — сравнение, слияние, реферти
- `compare_scenes(scenario, A, B)` → `{agreed, disputed: {field: (a,b)}}`.
  **Что считается «спором» по темам** (пороги для вызова рефери):
  - **facade**: `storeys` (Δ≥1), `width_m` (Δ>15%), `floor_height_m`
    (Δ>10%), `windows.rows×cols` (несовпадение), `windows.skip[][]`
    (Δ≥2 ячейки), `doors[]` count (Δ≥1).
  - **plan**: футпринты зданий (IoU <0.6 через shapely), `storeys`
    (Δ≥1), `width_m` (Δ>20%), `floors count` (Δ≥1).
  - **interior**: `rooms[]` count (Δ≥1), суммарная длина стен (Δ>15%),
    `doors[]` count (Δ≥1), `windows[]` count (Δ≥1), `room.w/h` (Δ>15%).
  Метрики согласия: counts, `metres_per_trace_pixel` (Δ%), `width_m`/
  `floor_height` (Δ%), IoU футпринтов (plan, shapely), совпадение
  `rows×cols` + skip-матрицы (facade), длины стен/число комнат (interior).
- `merge_scenes`: согласованное — из A (числа — среднее при |Δ|<порога);
  спорное — **реферти-вызов на ярус ВЫШЕ ремонта** (новая рулька
  `THREED_REFEREE_MODEL`, дефолт = `THREED_REPAIR_MODEL` повышен на
  одну ступень в каталоге; при дефолтном pipeline — sol вместо luna;
  при `THREED_MODEL=*` override — отдельное значение, не luna):
  картинка + оба варианта ТОЛЬКО спорных полей → выбор.
  **Лимит: ≤1 реферти-вызов на попытку** (см. `max_calls_per_attempt`
  в з.6) — иначе падаем в A + warning. Сбой/неуверенность рефери →
  вариант A + warning (не хуже текущего поведения).
- `confidence = {agree_rate, disputed_fields}` → pset `EnsembleAgreement`
  в IFC + дамп `_threed_last.json`. `agree_rate` далее используется
  как гейт регуляризации (з.4).

### Задача 4. Регуляризация по темам (чистый код, бесплатно)
- **Гейт**: регуляризация применяется ТОЛЬКО при `agree_rate ≥ 0.7`
  (выдача merge, з.3). При низком согласии — пропуск с warning
  «regularization skipped: low ensemble agreement», чтобы не ломать
  VLM-интент (пристройки, эркеры, намеренная асимметрия).
- **facade**: выравнивание ритма сетки (равные шаги в допуске 15%), снап
  `floor_height` к 0.05 м, симметрия сетки — только в зеркальных
  секциях с детекцией осевой линии (`|Δleft/right|<10%` → зеркалим
  худшую половину; несимметричные секции не трогаем).
- **plan**: ортогональный снап ТОЛЬКО для рёбер с `|α − k·90°| < 15°`,
  прочие рёбра — `min(α, 90−α)` (эркеры с α≈67.5° не ломаются), RDP
  упрощение при > 8 вершин; снятие взаимных пересечений футпринтов;
  МНК-масштаб по всем якорям из скилла `tools/image-to-ifc` сразу.
- **interior**: снап углов стен к `min(α, 90−α)` (всегда ближайший
  прямой/45°, не ломает эркеры с α≈67.5°), замыкание комнат (shapely),
  нормализация толщин (наружные 0.3–0.4 / перегородки 0.1–0.15).
  Кламп проёмов — константы `OPENING_MIN/HOST/MARGIN` из п.55 (общий
  импорт из `threed_scenarios`, не дублировать).
Применяется к сцене-победителю после merge (з.3), ДО контракта/сборки.

### Задача 5. Визуальный verify (оверлей) — `threed/threed_verify.py`
- `render_overlay(scenario, scene, image)` рендерит оверлей по
  **SCENE-победителю из з.3 ДО сборки** (PIL/matplotlib — паттерн
  `draw_overlay` из скилла `tools/image-to-ifc`, `tools/image-to-ifc/
  SKILL.md`). Это ловит ошибки АНАЛИЗА (главная цель), а не сборки
  (для сборки — `structural_report` п.58). Фасад — контур + сетка окон
  на картинке; план — полигоны; интерьер — стены/двери.
- `_verify_attempt` (router:474–486): судья получает **массив из двух
  dataURL** — оригинал + оверлей (а не одну «составную»), в одном
  VLM-запросе. Вопросы о выравнивании сетки/контура/массы → issues
  становятся геометрическими → CORRECTIONS в следующей итерации.
- **Стоимость**: payload растёт в ~2 раза (две картинки); учитывается
  в `max_calls_per_attempt` (з.6) и в таблице стоимости з.8.
- Инвариант сохраняется: verify не роняет генерацию.

### Задача 6. Интеграция в роутер + деплой
- `threed/threed_router.py` `_generate_impl`: после успешного анализа A
  при включённом двухканальном режиме — прогон B (grounding) →
  `compare_scenes` (з.3) → `merge_scenes` → регуляризация (з.4);
  затем существующие контракт→сборка→verify→петля. Сбой прогона B
  не роняет генерацию (warning, работаем с A).
- **Env (новые и обновлённые)**:
  - `THREED_ENSEMBLE` (0/1, дефолт 1) — выключатель двухканального
    режима целиком;
  - `THREED_ENSEMBLE_MODEL` (дефолт из зонда з.1b) — модель прогона B;
  - `THREED_REFEREE_MODEL` (дефолт = `THREED_REPAIR_MODEL` повышен
    на одну ступень в каталоге; sol для дефолтного pipeline) — модель
    арбитра споров (см. з.3);
  - `THREED_MAX_CALLS_PER_ATTEMPT` (дефолт 6) — лимит на суммарное
    число VLM-вызовов в одной попытке (analysis A + B + repair +
    verify + referee + escalation). Превышение → warning + переход

  - Тег стоимости `ensemble` в `_usage_stage`/тост.
- `setup_threed.py`: добавить новые файлы (`threed_ground.py`,
  `threed_ensemble.py`) в список копирования — **грабля п.58/п.56**:
  новый модуль без деплоя = `AttributeError` из venv-копии роутера.
  Деплой ДО тестов.
- После деплоя — обязательная проверка парсинга App-бандла

## 6. Порядок работ

0 → 1a (GT-боксы, ручная разметка) → 1b (зонд, выбор модели B) →
2 (конвертеры боксы→сцена) → 3 (compare+merge+referee) → 4
(регуляризация) → 5 (visual verify) → 6 (интеграция+деплой) → 7
(A/B-приёмка); после фасада — перенос конвертеров и регуляризации на
plan и interior (задачи 2–4 для остальных тем), повторный A/B.

**Логический поток данных**: A (analysis) + B (grounding) →
`compare_scenes` → `merge_scenes` (с реферти по спорам) → регуляризация
(только при `agree_rate ≥ 0.7`) → контракт/сборка/verify (существующие)
→ петля CORRECTIONS. Регуляризация (4) ПОСЛЕ merge (3), а не до —
иначе она регуляризует одну из сцен до сведения.

**Гейт между 1a и 1b**: 1a завершается с `_compute_iou(pred, gt) ≥ 0.9`
на ручных боксах — sanity разметки. Без этого 1b даёт IoU = 0 для всех
кандидатов, и архитектура выпадает в fallback «B = текстовый на другой
модели». Гейт НЕ блокирует реализацию задач 2–7, но блокирует
интерпретацию результатов зонда.

## 8. Риски и грабли

- Grounding-способность каталога нельзя предполагать — зонд задачи 1b
  решает (см. fallback выше).
- Деплой: setup_threed.py копирует список файлов; забыть новый модуль =
  AttributeError (п.58).
- Латентность +1 VLM-вызов (~20–60 с) — job-API уже асинхронный
  (поллинг), Semaphore(1) остаётся.
- Рефери может ошибаться: неуверенный вердикт → берём A + warning
  (текущее качество — нижняя граница).

### Стоимость: сценарии по темам

| Сценарий | A | B | repair | referee | verify | escal. | ∑ | cost USD |
|----------|---|---|--------|---------|--------|--------|---|----------|
| **facade, happy path** | 1 (astra) | 1 (qwen-vl) | 0 | 0 | 1 (astra) | 0 | 3 | ~$0.15 |
| **facade, w/ repair + issues** | 1 | 1 | 1 (luna) | 1 (sol) | 1 | 0 | 5 | ~$0.22 |
| **facade, worst (п.45)** | 1 | 1 | 1 | 1 | 1 | 1 (astra) | 6 | ~$0.30 |
| **plan** | 1 | 1 | 0 | 0 | 1 | 0 | 3 | ~$0.12 |
| **interior** | 1 | 1 | 1 | 0 | 1 | 0 | 4 | ~$0.20 |

Baseline (без ансамбля, п.45 живой): фасад 4 вызова / ~$0.20–0.30.
Двухканальный режим добавляет: +B вызов (~$0.04–0.06), +реферти при
спорах (~$0.005, ≤1 на попытку), +возможный verify с двойной картинкой
(payload ×2, но не вызов).

**Лимит `THREED_MAX_CALLS_PER_ATTEMPT=6`** защищает от разгона:
- escalation (отдельная попытка) НЕ считается в лимит attempt, но
  учитывается в общем лимите сессии (для отчёта в usage);
- превышение → warning + best-so-far, не 422.

`THREED_ENSEMBLE=0` откатывает в один клик (один analysis A, как до
п.56 — verify/repair/escalation опциональны).

Фасад первым; двухканальный режим через `THREED_ENSEMBLE=1` в .env

## 11. Критерии приёмки (измеримые)

Все метрики считаются в `tests/_e2e_3d_roundtrip.py` на N≥3 прогонов
на каждую из 3 картинок × 3 темы = 27 baseline + 27 нового pipeline.
Судья — модель `stage_models["verify"]` с промптом `SYSTEM_JUDGE` (тот
же, что в п.44 живой roundtrip); score ∈ [0, 100].

| Метрика | Baseline (п.45 живой) | Target (новый pipeline) | Считается как |
|---------|------------------------|--------------------------|----------------|
| **median judge-score, facade** | 43 | ≥ 51 (Δ ≥ +8) | median по 9 прогонам (3 картинки × 3 запуска) |
| **median judge-score, plan** | не измерено | ≥ baseline + 5 | то же |
| **median judge-score, interior** | не измерено | ≥ baseline + 5 | то же |
| **agree_rate**, facade | — (нет двухканального) | ≥ 0.7 | доля полей в `agreed`, не в `disputed` |
| **agree_rate**, plan/interior | — | ≥ 0.6 | то же |
| **IoU оверлея по GT**, facade | — | ≥ 0.6 median | mean IoU bounding-box'ов оверлея с GT из з.1a |
| **structural_report clean rate** | ~baseline | ≥ baseline | доля попыток с пустым `structural.issues` |
| **contract_issues reduction** | — | ≥ 30% reduction median | медиана числа issues контракта посадки |
| **median cost_usd** | ~$0.20 (фасад happy) | ≤ $0.40 (≤ 2×) | из `_usage_summary` |
| **`max_calls_per_attempt`** | n/a | 100% попыток в лимите | счётчик вызовов в попытке ≤ 6 |

**Baseline-прогон ОБЯЗАТЕЛЕН ДО старта задач 2+**: отдельный коммит в
ветке `baseline-3d`, прогон с `THREED_ENSEMBLE=0`, фиксация результатов
в `data/probe/_ab_baseline.json`. Без него Δ не измерим — стохастика
VLM даёт ±5–15 на одном входе (см. живой прогон п.45: 35→43 на двух
последовательных запусках).

**Если target не достигнут** — НЕ откатываем архитектуру (лишний
риск). Последовательность:
1. тюнинг порогов споров (з.3) — увеличить Δ → меньше реферти →
   меньше шума в `merge_scenes`;
2. тюнинг гейта регуляризации (з.4) — снизить `agree_rate` gate;
3. смена `THREED_ENSEMBLE_MODEL` (з.1b кандидат-2);
4. последний шаг — `THREED_ENSEMBLE=0` для проблемной темы (частичный
   откат, не архитектурный).
