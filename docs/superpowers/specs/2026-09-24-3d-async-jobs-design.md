# Спека: 3D Design — фоновые задачи генерации (фикс 524 за туннелем)

Дата: 2026-09-24. Ветка `interior`. Триггер: живая генерация интерьера
24.09 (план 807×650, gpt-6-astra) заняла 147 с — POST /api/v1/threed/generate
идёт синхронно, Cloudflare-туннель рвёт ответ на ~100 с → клиент видит
«HTTP 524», UI не узнаёт имя файла и не открывает модель, хотя бэкенд
успешно дописывает IFC (data/ifc/3D_interior_20260924-115205.ifc,
verify ok=true). Лимит CF бесплатный и не настраивается; пайплайн с
петлёй самопроверки законно занимает 2–6 минут (CHAT_TIMEOUT_S=180 на
каждый VLM-вызов, до 4 вызовов).

## Задача

Убрать зависимость «успех UI» = «один длинный HTTP-ответ»: генерация
выполняется в фоне, фронт опрашивает статус короткими запросами
(каждый укладывается в лимит туннеля с запасом). Бонус — живой прогресс
этапов вместо пустого таймера секунд.

## Дизайн

### threed/threed_router.py (бэк)

1. Job store в памяти процесса: `_jobs: dict[str, dict]` + lock;
   запись = `{id, status: queued|running|done|error, stage, scenario,
   created, ts, result, error}`; храним последние JOBS_MAX=20, готовые
   (done/error) старше JOBS_TTL_S=1800 удаляются при создании новой.
   Рестарт сервера = задачи пропадают: файлы-артефакты (IFC, дамплы)
   переживают рестарт, UI обрабатывает 404 поллинга сообщением.
2. `POST /generate` — ТОЛЬКО валидация тела + `_prepare_png` (быстрые
   отказы остаются 422 синхронно) → создание job → daemon-поток →
   мгновенный ответ `{"jobId": id, "status": "queued"}`.
3. Рабочий поток: `threading.Semaphore(1)` — одна VLM-генерация
   одновременно (деньги и память), остальные job'ы стоят в queued
   (порядок — по созданию).
4. Прогресс этапов: `_generate_impl(..., progress=None)` — callable,
   вызывается с кодами `analysis` (VLM-анализ) → `build` (сборка IFC) →
   `verify` (самопроверка). Роутер пишет их в job["stage"]; статусная
   строка UI локализует коды. Существующие вызовы (тесты) без progress
   не меняются.
5. `GET /v1/threed/jobs/{id}` → `{jobId, status, stage, scenario,
   elapsed_s, result?, error?}`; done-результат = прежнее тело ответа
   generate (`{name, warnings[, camHint][, verify]}`) — фронт после
   поллинга выполняет ту же обработку, что раньше делал после POST.
   Неизвестный id → 404.
6. Ошибка генерации (ValueError/Exception) — не 422, а job со
   status=error и error-текстом (прежний текст detail).

### imagerouter/devbim_topright_buttons.js (фронт)

1. `run3D`: POST → если в ответе есть `jobId` — поллинг
   `GET /api/v1/threed/jobs/{id}` каждые 2.5 с; если ответ уже содержит
   `name` (старый бэк) — прежняя синхронная ветка (обратная
   совместимость бесплатно).
2. Статусная строка модалки: `⏳ 47 s · Анализ плана` / `Сборка IFC` /
   `Самопроверка VLM` / `В очереди` (RU/EN через словарь t()).
3. done — прежняя обработка результата: тост warnings, localStorage
   lastModel/camHint, закрытие модалки, вкладка IFC, нота verify
   (✓ VLM / ⚠ issues). Поллинг живёт до done/error даже если модалку
   закрыли Esc — результат придёт тостом и переключением вкладки.
4. error — текст job.error в статусной строке, кнопка разблокируется.
   404 поллинга — «сервер перезапущен; готовые модели — вкладка IFC».

### Совместимость и деплой

- Сигнатура `_generate_impl` расширяется optional-параметром — тесты
  фаз 1–4 не меняются. `setup_threed.py` копирует as-is (без правок).
- `setup_imagerouter.py` `deploy_topright_buttons` копирует виджет
  as-is (без правок) — но перезапуск сервера нужен для роутера
  (launch\_restart_server.ps1).
- E2E-смоук без VLM: job с неизвестным сценарием ("attic") проходит
  весь цикл job-API (queued → running → error с текстом гейта).

## Не делаем (в этой задаче)

- Персистентность job'ов (БД/файл) — артефакты и так переживают
  рестарт, очередь из одного семафора терять нечего.
- Кнопка Cancel, история задач в UI, прогресс в процентах — не просили.
- Двухпроходный конвейер геометрии (эксперименты v3) и «регенерация
  с ассетами» — отдельные фазы (пользователь в курсе).
