# Спека: многопользовательский режим «users» — вход по email/паролю + персональный токен ImageRouter

Дата: 2026-10-07. Ветка: `user_control`.

## Контекст

Сервис (один экземпляр InvokeAI на ПК владельца) открывается наружу через
публичный адрес/туннель — нужно много пользователей на одном экземпляре.
Пользователь заходит на сервис, видит окно входа с полями: почта, пароль,
токен ImageRouter. Ключи ImageRouter владелец создаёт лично на imagerouter.io
и выдаёт каждому пользователю. Все рабочие файлы (картинки, IFC, PDF,
3D-результаты) должны быть привязаны к пользователю.

Уже существует (SSO-ветка, выключена в `.env`: `STUDIO_AUTH_MODE=password`):

- `siteauth/studio_store.py` — оверлей-БД `data/studio.sqlite` (таблицы
  `users`, `ownership`), HMAC-сессии (`devbim_session`), роли, сокет-комнаты;
- `siteauth/site_auth.py` — SiteAuthMiddleware: режимы password/sso, инжект
  заголовка `x-studio-user`, фильтрация списков по владению, гейты
  destructive-эндпоинтов, админ-панель `/admin`;
- пер-пользовательская изоляция картинок/бордов/очереди (ownership-фильтр);
- `ifc/`, `pdf/`, `threed/` уже читают `x-studio-user` и проверяют владение.

Нет: входа по email/паролю (SSO ждёт JWT от devbim.com), персональных токенов
ImageRouter (один `IMAGEROUTER_API_KEY` на всех), физических per-user папок
для IFC/PDF/3D.

## Цели

1. Новый режим `STUDIO_AUTH_MODE=users`: страница входа с полями
   «Почта», «Пароль», «Токен ImageRouter (необязательно, если уже сохранён)».
2. Персональный токен ImageRouter: вводится один раз при первом входе (или
   задаётся админом), хранится сервер-side в `studio.sqlite`, используется во
   ВСЕХ облачных вызовах от имени пользователя: генерация на канвасе,
   правки/референсы, апскейл, Prompt Enhancer, VLM-аналитик 3D, `/credits`.
3. Аккаунты создаёт только админ: панель `/admin` и CLI `user_manager.py`.
   Саморегистрации нет.
4. Изоляция рабочих файлов по пользователю:
   - картинки — общая галерея InvokeAI + владелец (готовый механизм,
     физическое разделение невозможно без форка InvokeAI);
   - IFC/PDF/3D — физические подпапки `data/ifc/<почта>/…`,
     `data/pdf/<почта>/…`; в API имена остаются плоскими (фронт не меняется).
5. Прежние режимы (password, sso) не ломаются; компании-экземпляры живут
   как раньше (у них свой `.env`).

## Не-цели

- Саморегистрация и восстановление пароля по почте (нет почтового сервера).
- Отдельный экземпляр на пользователя (для этого есть компании, порты 9100+).
- Per-user локальные модели InvokeAI (менеджер моделей общий).
- Физическое разделение картинок по папкам.

## Принятые решения (развилки; вопросы задавались 2026-10-07, ответов не было — зафиксированы дефолты)

| Развилка | Решение | Почему |
|---|---|---|
| Изоляция файлов | Подпапки `data/ifc/<почта>/` + владение картинками | Честное разделение «по почте» на диске, лёгкий бэкап на пользователя; картинки иначе почти никак |
| Токен IR | Один раз при входе → сохраняется в профиле | UX: без повторного ввода; смена — повторным вводом или через админа |
| Аккаунты | Создаёт админ (панель + CLI), без саморегистрации | Лицензионная модель, публичный адрес |
| Окно входа | Серверная страница `/auth/login` (не DOM-модалка) | Уже есть стиль DevBIM, работает без JS, единый механизм с sso-режимом |

## Архитектура — по файлам

### `siteauth/studio_store.py` (задеплоен `setup_site_auth.py`)

- Миграция таблицы `users`: `ALTER TABLE … ADD COLUMN` `password_hash TEXT`,
  `ir_token TEXT` (проверка по `PRAGMA table_info` — идемпотентно).
- `user_id` для локальных аккаунтов: `u_` + `sha256(email.lower())[:16]`;
  уникальный индекс по `lower(email)`; вход — поиск по `lower(email)`.
- Новые функции:
  - `create_user(email, name, password, role="user", ir_token=None) -> dict`
    (роль `user|admin`; email-формат проверяет вызывающий);
  - `find_user_by_email(email) -> dict | None`;
  - `set_password(user_id, password)` / `check_password(user_id, password)`;
  - `set_ir_token(user_id, token | None)` / `get_ir_token(user_id)`;
  - `auth_mode() -> "password" | "sso" | "users"` (одна точка чтения
    `STUDIO_AUTH_MODE`).
- Пароли: PBKDF2-HMAC-SHA256, 240 000 итераций, соль 16 байт;
  формат `pbkdf2_sha256$240000$<salt_hex>$<hash_hex>` (только stdlib);
  сравнение `hmac.compare_digest`.
- `room_for_environ`: комната сокета теперь для режимов `sso` И `users`
  (сейчас условие `!= "sso"` → None; меняется на `== "password"` → None).
- Токен в браузер никогда не отдаётся (только флаги `has_token`).

### `siteauth/site_auth.py`

- `_mode()`/общая ветка: секция sso распространяется на `users`
  (`mode in ("sso", "users")`): проверка сессии, `/api/v1/studio/me`,
  `/admin`, инжект `x-studio-user`, ownership-фильтры, CSP, ws-гейт 4001.
- `/auth/sso` в режиме `users` тоже работает (если задан
  `STUDIO_JWT_SECRET`) — задел на интеграцию devbim.com.
- `/auth/login` в режиме `users`:
  - GET — форма: Почта / Пароль / Токен ImageRouter (необязательно);
    подсказка «Забыли пароль — обратитесь к администратору»; ссылка не нужна.
  - POST (form-urlencoded):
    - пустая почта + пароль == `SITE_PASSWORD` → сессия `admin-local`
      (вход владельца-админа, как в sso-режиме);
    - иначе: поиск по `lower(email)`; нет пользователя/неверный пароль →
      401 «Неверная почта или пароль» + sleep 0.3 c; `revoked` → 403
      «Учётная запись заблокирована»;
    - если поле токена непусто — проверка и сохранение (см. ниже);
    - минт сессии `devbim_session` → 303 на `/`.
  - в режиме `sso` — прежнее поведение (вход админа по SITE_PASSWORD).
- Проверка токена при вводе: `POST https://api.imagerouter.io/v1/auth/test`,
  Bearer <токен>, таймаут 15 c (в потоке, не в event loop):
  HTTP 200 → сохранить; 4xx → отказ входа «Токен ImageRouter отклонён»;
  сетевой сбой/5xx → сохранить с предупреждением в лог (не запираем
  пользователя при лежащем апстриме). Вызов вынесен в функцию
  `_validate_ir_token(token)` (переопределяется в тестах).
- Кука сессии: `HttpOnly; SameSite=Lax; Max-Age=<STUDIO_SESSION_TTL>` —
  флаг `Secure` убирается и в sso-режиме: туннель может терминироваться
  в http (иначе кука не придёт).
- Fail-closed по секрету: пустой `STUDIO_SESSION_SECRET` → `_session_user`
  возвращает None, логин отклоняется страницей «Сервер не настроен»
  (пустой секрет сделал бы HMAC-сессии подделываемыми).
- `/api/v1/studio/me` отдаёт `"mode": "users"` и реальные email/имя/роль.
- Админ-панель `/admin` (режимы sso/users):
  - таблица показывает ВСЕХ пользователей, кроме `admin-local` (сейчас
    скрываются и роль-admin — для локальных аккаунтов это неудобно);
  - в списке добавляются `has_password`, `has_token` (не значения!);
  - новые эндпоинты (только admin):
    - `POST /admin/api/users` `{email, name?, password, role?, token?}` —
      создать (валидация: email-формат, пароль ≥ 8 символов,
      роль `user|admin`); 409 при существующем email;
    - `POST /admin/api/users/{id}/password` `{password}` — смена пароля;
    - `POST /admin/api/users/{id}/token` `{token}` — задать/очистить токен
      (`""` → очистить), с той же проверкой на апстриме;
  - в UI: форма «Создать пользователя» + кнопки «Пароль…»/«Токен…»
    (window.prompt) в строке таблицы.

### `imagerouter/imagerouter_router.py` (задеплоен `setup_imagerouter.py`)

- Новая точка выбора ключа: `effective_key(studio_user) -> str | None`:
  1. есть `studio_user` и в `users` есть `ir_token` → персональный токен;
  2. есть `studio_user`, аккаунт с ролью `user` и токена НЕТ → `None`
     (глобальный ключ НЕ подставляется — иначе пользователь жжёт кредиты
     владельца; генерация упадёт с понятной ошибкой
     «Персональный токен ImageRouter не задан — обратитесь к администратору»);
  3. нет аккаунта (`admin-local`) или роль `admin` без своего токена →
     прежний `_load_key()` (глобальный `.env`/`imagerouter.json`).
- Замена `_load_key()` на `effective_key(studio_user)` в:
  - `_handle_canvas_generation` / `_handle_upscale_generation`
    (studio_user уже приходит параметром);
  - эндпоинт Prompt Enhancer (добавить `request: Request` → читать
    `x-studio-user`);
  - `GET /credits` и `GET /status` (добавить `request`; `/status` показывает
    подсказку ключа пользователя, `key_source: "user"`).
- `GET /models` (каталог) остаётся на глобальном ключе без авторизации —
  каталог одинаков для всех ключей.

### `threed/threed_router.py`

- `POST /generate`: пользователя (`x-studio-user`) сохранять в job и
  передавать в конвейер:
  - `out_dir = data/ifc/<slug-пользователя>/` (свой каталог);
  - VLM-вызовы — через `imagerouter.effective_key(user)` вместо
    прямого `_load_key()` (сейчас `from …imagerouter import _load_key`);
- Фикс давнего зазора: готовый IFC-файл тегируется `tag("ifc", name, user)`
  (сейчас тегируется только job — обычный пользователь не видит свой
  результат во вкладке IFC).
- Превью `3D_…_preview.png` пишется в тот же per-user каталог.

### `ifc/ifc_router.py`, `pdf/pdf_router.py` — физические per-user подпапки

- Каталог пользователя: `data/ifc/<dir(email)>/`, где `dir(email)` =
  `email.lower()`, разрешены `[a-z0-9@._+-]`, прочее → `_`, без ведущих/
  хвостовых точек, ≤ 80 символов (имена папок читаемы и «завязаны на почту»;
  коллизия возможна только у экзотических email, отличающихся запретными
  символами, — принято).
- `upload` — пишется в подпапку пользователя (для `admin-local`/без
  пользователя — в корень, прежнее поведение); тег владения сохраняется
  (счётчики админ-панели).
- `list` — пользователь: файлы своей подпапки + файлы корня, тегированные
  ему (легаси); админ: корень + все подпапки (в ответе появляется поле
  `owner` — email владельца); при совпадении имён в разных подпапках админ
  видит оба (известное упрощение).
- `file/{name}`, `DELETE /file/{name}` — разрешение пути: своя подпапка →
  корень (видимость прежняя: чужое/без владельца — 404 для не-админа);
  админ ищет по корню + подпапкам (порядок: корень, затем подпапки по
  алфавиту).
- password-режим (без `x-studio-user`) — поведение дословно прежнее
  (совместимость с компаниями).

### `user_manager.py` (новый, корень репо — по образцу `company_manager.py`)

CLI управления пользователями (работает с той же `studio.sqlite`,
`--root <путь>` для компаний, дефолт `./data`):

- `add <email> [--name] [--role user|admin] [--password …] [--token …]`
  — без `--password` генерирует читаемый пароль (слово-слово-4цифры,
  как `company_manager.gen_password`) и печатает;
- `list` — таблица email/имя/роль/токен?/заблокирован/последний вход;
- `set-password <email> [--password …]`;
- `set-token <email> <token|->` (`-` — очистить);
- `role <email> user|admin`; `revoke <email>` / `restore <email>`.

### `devbim_banner.js`

Чип пользователя (`email · роль` + «Выйти») показывается и в режиме
`users`: условие `d.mode !== 'sso'` → `d.mode !== 'sso' && d.mode !== 'users'`.

### `setup_site_auth.py`

- `ensure_env`(): добавляет `STUDIO_SESSION_SECRET=<сгенерирован secrets.token_hex(32)>`
  если отсутствует (для sso раньше преднамеренно не добавляли — для users
  секрет обязателен, см. fail-closed).
- Режим в `.env` не переключает (дефолт `password` для новых установок);
  включение — правкой `.env` (см. «Развёртывание»).

## Потоки

### Вход
1. Неавторизованный запрос → 303 на `/auth/login` (API → 401).
2. POST email+пароль(+токен) → проверка → кука `devbim_session` → 303 `/`.
3. Каждый запрос: HMAC-кука → `effective_role` (override/revoke мгновенны) →
   инжект `x-studio-user` → ownership-фильтры (как в sso).

### Генерация с персональным ключом
1. Канвас: `enqueue_batch` → ImageRouterCanvasMiddleware → studio_user из
   scope → `effective_key(studio_user)` → Bearer в апстрим.
2. Пользователь без токена → 422 с сообщением «обратитесь к администратору».
3. Результат пишется в общую галерею с тегом владения (как сейчас).

### Файлы
- IFC/PDF upload → своя подпапка + тег; list/file/delete — только свои
  (админ — все); 3D-результат IFC — в подпапку пользователя + тег.

## Безопасность

- Пароли только хэши (PBKDF2), сравнение constant-time; подбор — sleep 0.3 c.
- Токен IR хранится в `studio.sqlite`, в браузер не отдаётся (только
  `has_token`/последние 4 символа в подсказке `/status`).
- Спуфинг `x-studio-user` вырезается мидлварью (уже есть).
- Пустой `STUDIO_SESSION_SECRET` → вход запрещён (fail-closed).
- Регулярки гейтов/фильтров не меняются — контракты `test_studio_*`
  сохраняются.

  revoked → 403; вход админа (пустая почта + SITE_PASSWORD); logout;

- `tests/test_userauth_token.py` — `effective_key`: персональный токен

## Развёртывание / миграция

1. Применить сетапы (порядок не меняется):
   `setup_imagerouter.py` → `setup_ifcviewer.py` → `setup_pdfviewer.py` →
   `setup_designcode.py` → `setup_threed.py` → `setup_site_auth.py`
   (последний копирует обновлённые `site_auth.py`/`studio_store.py` и
   генерирует `STUDIO_SESSION_SECRET`).
2. В корневом `.env`: `STUDIO_AUTH_MODE=users`.
3. Перезапуск `launch\_restart_server.ps1`.
4. Владелец входит: пустая почта + `SITE_PASSWORD` → `/admin` → «Создать
   пользователя» (или `python user_manager.py add …`) → выдаёт человеку
   пароль + его ключ ImageRouter.
5. Легаси-файлы в корнях `data/ifc`, `data/pdf` остаются видимыми админу.
