# Дизайн: tiered-конвейер 3D — дешёвое извлечение, детерминированный контракт, эскалация на дорогую модель

Дата: 24.09.2026. Ветка: `interior`. Пункт HANDOFF: п.56. Решение по
итогам обсуждения с пользователем (сессия 24.09): предложения
«генерация за 2 прохода (извлечение → ТЗ сборщику)» и «дешёвые модели
в цикле собрать→проверить→повторить» сведены к гибриду — платим за
дорогую модель только когда дешёвая доказала, что не справляется.

## Проблема

1. **Одна дорогая модель на всё.** Извлечение сцены и verify крутятся
   на одном THREED_MODEL (дефолт `openai/gpt-6-astra`, ~$0.22 на
   планировку). Дешёвые ярусы каталога ImageRouter не задействованы:
   sol ~$0.045, luna ~$0.003 (тарифы за 1M токенов: astra $10/$50,
   sol $2/$10, luna $0.1/$0.5 — замеры п.53 HANDOFF).
2. **Цикл без суда не спасает.** Петля самокоррекции уже есть
   (`_generate_impl`: verify → CORRECTIONS → `_r2`, победитель по
   рейтингу), но генератор и судья — одна модель. Переход «в лоб» на
   sol даёт эхо-камеру: слабый verify штампует ok на плохой сборке;
   систематические ошибки восприятия (неверно прочитанная стена)
   повтор от той же модели по той же картинке не чинит.
3. **Класс ошибок «посадка» ловится поздно и молча.** Проём вне
   стены-носителя / огрызок < 0,6 м сейчас нормализуется в сборщике
   (п.55): без предупреждения, после оплаты сборки и verify, факт
   промаха VLM теряется. Замеры п.55: окно за торцом на 0,21 м,
   дверь на огрызке 0,2 м под 90° — validate_scene такое не видит
   (клампит величины, не посадку).

## Решение — четыре слоя

Цепочка: **извлечение (sol) → контракт кодом (бесплатно) → ремонт
(luna/sol, только при нарушениях) → сборка → verify (astra) →
эскалация (astra, одна попытка при провале дешёвых)**. Существующая
петля verify/CORRECTIONS и рейтинг попыток сохраняются; меняется
маршрутизация моделей и добавляется суд до сборки.

### Часть 1. Контракт посадки кодом (threed/threed_scenarios.py)

- Константы п.55 выносятся из build_interior в общие
  (OPENING_MIN_HOST = 0.6, OPENING_MARGIN = 0.05, OPENING_MIN = 0.3);
  сборщик импортирует их (поведение п.55 не меняется — последний рубеж
  остаётся).
- `validate_scene` (interior) после существующих клампов величин
  проверяет посадку и возвращает нарушения двумя корзинами:
  - **нормализуемые кодом** (кламп центра проёма в сегмент, ширина ≤
    длина − 0.1, высота ≤ wall_height − sill − 0.05, перенос проёма с
    огрызка на ближайшую подходящую стену ≥ 0.6 м): правим на месте,
    каждое — warning «посажено» (сегодня сборщик делает это молча);
  - **семантические** (мебель вне комнат, комната не замкнута стенами,
    проём без стены-носителя рядом): в `issues` — вход ремонта (часть 2)
    и, если доживут до verify, в CORRECTIONS.
- Проёмы `wall_idx:"outline"` не проверяются на посадку (нет
  носителя) — как сейчас.

### Часть 2. Поэтапные модели (threed/threed_router.py, .env)

Новые рульки (имена — по образцу THREED_VERIFY*):

| Переменная | Стадия | Дефолт |
|---|---|---|
| `THREED_ANALYSIS_MODEL` | извлечение сцены | astra (до A/B, см. часть 4) |
| `THREED_REPAIR_MODEL` | JSON-ремонт по issues | luna |
| `THREED_VERIFY_MODEL` | verify превью vs исходник | astra |
| `THREED_ESCALATION_MODEL` | финальная попытка | astra |

- `THREED_MODEL` остаётся полным override: задан (env или file-store
  через PUT /api/v1/threed/model) → все стадии на нём, поведение как
  сегодня. Механизм file-store/env/дефолт (`_load_model_choice`)
  расширяется до per-stage с теми же приоритетами; PUT модели
  валидирует id по каталогу ImageRouter (как сейчас).
- **Ремонт**: вход — JSON сцены + issues (без картинки: это
  числовая/семантическая правка, зрение не нужно). Выход — тот же
  strict-JSON; гейт — повторная `validate_scene` + parse; не
  парсится/не проходит → один повтор на sol; не помогло → issues едут
  в CORRECTIONS следующей итерации (как сегодня). Вызывается ТОЛЬКО
  при непустых семантических issues — счастливый путь не платит.
- `_usage_stage` расширяется: `analysis | repair | verify |
  escalation` — в cost-дампах видно, какая стадия сколько съела.

### Часть 3. Эскалация (threed_router.py)

- Раунд остаётся как сейчас: попытки 1..K на analysis-модели
  (K = 1 + THREED_VERIFY_ITERS, по умолчанию 2). Если после раунда
  лучший вердикт ok=False (или все ok=None) и analysis ≠ escalation →
  +1 финальная попытка на эскалационной модели с полным накопленным
  CORRECTIONS (issues verify + семантические issues контракта).
  Именование файлов `_r{attempt_no}` — как сейчас.
- Отключаемо: пустой `THREED_ESCALATION_MODEL` → выключено.
- Победитель — по действующему рейтингу попыток (ok=True > меньше
  issues > ok=False бьёт ok=None > последняя).

### Часть 4. A/B-приёмка дефолта (до смены анализа на sol)

- Проба `data/probe/_probe_threed_tier.py` (паттерн проб п.53): гоняет
  N фиксированных планов (data/probe/plans/*.png — 5–8 реальных планов
  пользователя) на {astra, sol} × {контракт+ремонт вкл}, метрики по
  cost-дампам и history: first-pass ok, итераций до ok, суммарная
  стоимость, время.
- Критерий переключения дефолта analysis на sol: ≥ 70% планов ok
  ≤ 2 итераций И средняя стоимость прогона ниже astra. Не выполнили —
  дефолт остаётся astra, механика (контракт/ремонт/эскалация) всё
  равно полезна и безопасна.

## Проверка

- `tests/test_threed.py`: (а) инварианты контракта — фикстуры кейсов
  п.55 (окно за торцом → посажено с warning; огрызок → перенос или
  issues; мебель вне комнаты → issues); (б) маршрутизация моделей
  моком `_call_vlm`: порядок analysis→repair→verify→escalation,
  override THREED_MODEL глушит per-stage, пустая эскалация выключена;
  (в) ремонт-гейт: кривой JSON ремонта → повтор на sol → CORRECTIONS.
- Живой прогон 2–3 планов, сверка cost-дампов по стадиям.
- Регресс: существующие test_threed / test_threed_verify — без правок
  поведения при дефолтных настройках.

## Риски

- sol систематически плохо читает рукописные планы → эскалация
  страхует качеством, A/B (часть 4) страхует деньгами (дефолт не
  меняем без данных).
- luna ломает strict-JSON → гейт части 2 (validate + один повтор на
  sol), генерация не падает.
- Латентность: +1 вызов ремонта только при issues, эскалация — одна;
  кэп итераций существующий (THREED_VERIFY_ITERS ≤ 2).
- Эхо-камера исключена конструктивно: verify всегда ≥ sol по ярусу
  (дефолт astra), ремонт касается только контракта, не вердикта.

## Совместимость и откат

- Не задано ничего нового → поведение и стоимость сегодняшние
  (всё на astra, кроме бесплатного контракта и warning'ов «посажено»).
- Откат per-stage — удалением новых переменных из .env; контракт
  посадки — чистая добавка до сборки, откат не требуется (п.55 в
  сборщике остаётся).
